# Genesis device inventory and recovery boundary

## Implemented prototype
The genesis-core/device-inventory.mjs module provides SQLite-backed device metadata after a trusted server has authenticated the account:
- Random opaque device identifiers generated by the server.
- Account-scoped device listing and persistent metadata.
- Label/platform validation and a configurable active-device limit.
- Last-seen updates with monotonic timestamp checks.
- Per-device and account-wide revocation.

A device ID is metadata, not a credential and never proves identity. This prototype does not bind a browser passkey credential to a device record, associate session tokens with device IDs, or automatically revoke durable sessions when a device is revoked. Those integrations must be implemented server-side as one transaction or a carefully designed revocation workflow.

## Recovery design requirements
A replacement iPhone must not gain access merely by claiming the same account identifier. Recovery must verify an independent factor or a deliberately provisioned recovery secret, then require re-enrollment of a new passkey. A lost device must be revocable without access to that device.

Before production recovery:
1. Define an offline recovery kit with a high-entropy one-time recovery secret, generated under a reviewed threat model. Do not use security questions, SMS alone, or public profile details.
2. Store only a salted, memory-hard verifier for recovery secrets; rate-limit attempts and apply progressive delays/alerts. Never log or return the secret.
3. Make recovery codes single-use and atomically consume them. Provide a regeneration flow that invalidates prior codes.
4. Require an explicit recovery ceremony, notify existing trusted channels/devices where possible, and apply a cooling-off period for high-risk changes.
5. After recovery, revoke old sessions and optionally all old device/passkey credentials; enroll a replacement passkey and issue fresh sessions only after verified completion.
6. Provide encrypted export/import for memory continuity separately from identity recovery. Account recovery must not automatically decrypt a memory vault unless its independent vault key is available.
7. Test lost-phone, stolen-session, recovery-code replay, concurrent recovery, cross-account isolation, and account-takeover scenarios.

## Current limitations
No recovery secret, recovery endpoint, passkey-to-device binding, session/device cascade revocation, browser login UI, hosted HTTPS service, or production deployment is implemented. Device metadata is stored in SQLite, but the application must supply secure database location, filesystem permissions, encryption-at-rest/backup policy and operational controls.
